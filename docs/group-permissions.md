# User groups and permissions

Create groups at `/admin/groups/add` or `/admin/customer-groups/add`. Both routes use the same permission picker and the real Groups API. Group codes are generated by the backend. Search permissions by name, code or module, choose individual functions or a module, and review the selected count before saving.

The form creates an active group using `POST /api/v1/groups/create`, then assigns selected functions through `POST /api/v1/group-permissions/create/`. If an assignment fails, the form keeps the created group ID and successful assignments; retry sends only remaining assignments. Do not refresh a partially completed form: those retry details are held in memory. The backend rejects missing/deleted groups and inactive/deleted functions.

Create users at `/admin/customers/add`. Active groups and direct function permissions are selectable; the existing creation request sends `group_ids`, `permission_ids`, and `role_ids`. Group membership inherits group permissions; direct permissions are additive. Role selection remains the existing configured numeric role ID.

`GET /api/v1/user/access` returns the authenticated actor's effective permission codes. It reuses the existing authorization query and validates account status and identity; it cannot inspect another user by passing an ID. Spring Security still authenticates this endpoint. It is excluded from the legacy API-permission interceptor to avoid requiring a grant just to discover one's own grants.

The admin route guard refreshes permissions on navigation. Mapped navigation sections and product/group action controls use the same codes. Missing permissions, failed lookups, inactive groups and inactive/deleted grants do not authorize mapped pages. Account/token changes invalidate the UI's prior access. Direct navigation to a denied page shows an access-unavailable page. Unmapped sections retain their existing role guards; UI filtering is not a replacement for service authorization. Existing backend ADMIN bypass behavior and AI-specific restrictions are unchanged.

Group endpoint permission mappings are registered by the existing auth initializer on startup. No permission grants are automatically added to existing users or groups.

Validation: focused Angular tests cover selection, request payloads, partial retries, denied actions and stale account responses. Backend tests cover the self-access endpoint, disabled accounts, inherited permission revocation and invalid group assignments.

Large directories: function definitions are fetched in batches of 1,000 instead of 20. The picker initially renders at most 100 permissions. Search covers all loaded active definitions; Show more reveals another 100. Module selection and Select results apply to all matching definitions, including those outside the visible slice.

Live read-only checks passed through the local gateway: admin sign-in, self-access identity, group creation/assignment permission codes, and group listing. The database currently contains 10,055 effective permission codes for the local admin. Browser rendering verification was blocked by repeated browser-control timeouts; no live group grants or user creation were performed.
